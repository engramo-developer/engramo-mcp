Cut a release of `engramo-mcp` at the version in $ARGUMENTS (e.g. `v1.2.0`), or — if no version was given — at the current `Cargo.toml` version with the **patch** component incremented by 1.

The release itself is published by `.github/workflows/release.yml`, which fires on a pushed `v*` tag. This command's job is to land the version bump on `main` and then, only on explicit approval, push the tag that triggers the real publish.

---

## Step 0 — Decide which half of the release this run is

A release spans two invocations: one to land the bump, one to tag it after the PR is merged. Which half you are in is **read from the repo, never remembered from a previous run** — a later invocation has no memory of an earlier target version.

```bash
git checkout main && git pull
MAIN_VERSION=$(awk -F'"' '/^version = /{print $2; exit}' Cargo.toml)   # same parse release.yml uses
git ls-remote --tags origin "refs/tags/v$MAIN_VERSION"
```

- **Tag `v$MAIN_VERSION` missing** → a bump is merged but unreleased. This is a **tag run**: the target is `$MAIN_VERSION` — go straight to **Step 5**. Do not bump again.
- **Tag `v$MAIN_VERSION` exists** → the last version is already published. This is a **bump run**: continue to Step 1.
- **`$ARGUMENTS` names a version higher than `$MAIN_VERSION`** → always a bump run, even if the tag is missing.

Say which half you are in and why before acting: *"main is at 1.1.4 and v1.1.4 isn't tagged — this is a tag run, not a new bump."* If the state is ambiguous (e.g. the tag is missing **and** the user passed the same version), stop and ask.

### Resolving the target version (bump run only)

Let `CURRENT=$MAIN_VERSION`.

- **`$ARGUMENTS` given:** it must match `^v?[0-9]+\.[0-9]+\.[0-9]+$`. Strip any leading `v` — `Cargo.toml` carries the bare version, tags carry the `v`. If it does not match, **stop and ask**; never silently fall back to a patch bump on a typo.
- **`$ARGUMENTS` empty:** patch bump.
  ```bash
  NEXT=$(echo "$CURRENT" | awk -F. '{printf "%d.%d.%d", $1, $2, $3+1}')
  ```

Then state plainly: `1.1.3 → 1.1.4`.

## Step 1 — Preflight (all must pass before any edit)

- [ ] Working tree is clean (`git status --short` empty) — if not, stop and ask what to do with the changes.
- [ ] You are on an up-to-date `main` from Step 0. Do **not** assume the current branch is still the one from earlier work — a merged PR leaves you on a stale branch, or back on `main`.
- [ ] Target version is strictly greater than `$CURRENT`.
- [ ] The tag does not already exist: `git tag --list "v$NEXT"` is empty, and `git ls-remote --tags origin "refs/tags/v$NEXT"` is empty. A re-used tag would edit an already-published release.

## Step 2 — Bump

Exactly two files change — nothing else in the repo carries the version:

1. `Cargo.toml` — the `version = "..."` line in `[package]` only.
2. `Cargo.lock` — regenerated, not hand-edited: `cargo check` rewrites the `engramo-mcp` entry.

Do **not** touch `npm/**/package.json`; those stay at `0.0.0` on purpose and are stamped at publish time by `release.yml`. Do not create or edit a changelog — this repo has none and release notes are auto-generated by `generate_release_notes`.

## Step 3 — Verify (mandatory gate)

```bash
cargo fmt --all
cargo check
cargo clippy
cargo test
```

All four must exit cleanly before committing. Report the test count. This gate is ~1 minute on a warm build — never skip it, never background it.

## Step 4 — Branch, commit, push, PR

```bash
git checkout -b chore/bump-version-$NEXT
git add Cargo.toml Cargo.lock
git commit -m "chore: bump version to $NEXT"   # + the standard attribution trailers
git push -u origin chore/bump-version-$NEXT
gh pr create --title "chore: bump version to $NEXT" --base main --body-file <file>
```

- Branch name: `chore/bump-version-X.Y.Z`. Commit and PR title: `chore: bump version to X.Y.Z` — this matches every prior bump in the history.
- End the commit message with the `Co-Authored-By:` / `Claude-Session:` trailers and the PR body with the `🤖 Generated with [Claude Code]` footer, exactly as the session's active attribution guidance specifies. Never hardcode a session URL copied from this file.
- PR body: one-line summary plus the verification results (the four gate commands and the passing test count).
- Never commit the bump straight to `main`.

Report the PR URL, then **stop — this run is over.** Tell the user to merge the PR and then invoke `/release` again, which Step 0 will route to the tag run. Never fall through to Step 5 in the same run: the PR is not merged yet, so the tag would point at a commit whose `Cargo.toml` still holds the old version.

## Step 5 — Tag and publish (reached only via a tag run from Step 0)

**This step publishes to npm and creates a public GitHub release. It is irreversible.** Re-invoking `/release` on a merged-but-untagged `main` is itself the request to publish — but state what is about to happen (`tagging v$TARGET → publishes @engramo/mcp to npm`) and get a yes before pushing the tag. Never reach this step by falling through from Step 4.

Preconditions, each verified, not assumed:

- [ ] You are on an up-to-date `main` (Step 0 already did `checkout main && pull`).
- [ ] `main`'s `Cargo.toml` reads `$TARGET`, and the bump commit for it is present in `git log` (`chore: bump version to $TARGET`).
- [ ] `v$TARGET` does not exist locally or on `origin`.

```bash
git tag "v$TARGET"         # tags the squash-merged bump commit on main
git push origin "v$TARGET"
```

The tag push starts `release.yml`: it builds four platform binaries, creates the GitHub release, and publishes `@engramo/mcp` plus the four platform packages to npm with provenance. Report the run URL (`gh run list --workflow=release.yml --limit 1`) and let the user watch it; do not poll it in a tight loop.

To rehearse without publishing, use the workflow's own dry-run path instead of a tag:

```bash
gh workflow run release.yml -f dry_run=true -f version=$TARGET
```
